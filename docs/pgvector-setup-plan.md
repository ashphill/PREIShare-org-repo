# PREIshare pgvector setup plan

## Purpose

This plan turns on vector storage in our Supabase Postgres database so PREIshare can do semantic property search. It follows `docs/embedding-data-model.md`. It is the contract for the next step, the SQL migration. There is no seed data, embedding generation, search function, API or UI work here.

## Source of truth

All names and sizes below are copied from `docs/embedding-data-model.md`. If they ever disagree, fix the model doc first, then this plan.

| Item | Value (from the model) |
| --- | --- |
| Data model doc | `docs/embedding-data-model.md` |
| Table | `properties` (a new sample table, separate from Sprint 4's `property_listings`) |
| Primary key | `id`, UUID, generated by the database |
| Listing columns | `title` (text, required, not empty), `description` (text, required, not empty), `city` (text, optional), `property_type` (text, optional), `price` (whole US dollars, optional), `created_at` (timestamp, required, set by the database) |
| Embedding column | `embedding` |
| Embedding dimension | **1536**: the model doc's DIMENSION_TODO, set to 1536 for the planned model OpenAI `text-embedding-3-small` |
| Embedding nullability | **Nullable**: null until seed or backfill fills it; rows with a null embedding are not searchable |
| Ranking style | Cosine distance, using pgvector's `<=>` operator (lower distance = closer meaning) |

**Gaps found in the model:** none blocking. The model had left the table name and the number for DIMENSION_TODO open, and both are now filled in there (`properties`, 1536). The model doesn't mention security for the new table, so a minimal safe default is added as migration goal 4 below.

## Migration goals (what "done" means)

1. The pgvector extension (`vector`) is enabled in the database.
2. The `properties` table exists with exactly the model's columns, plus `embedding` as `vector(1536)`.
3. `embedding` is allowed to be null, because seeding and backfill come later.
4. Row-level security is **on** for `properties`, with one read-only policy so search can read the sample rows. There are no insert, update or delete policies, so the browser can't write to the table. Seeding happens later through the SQL editor or trusted server code.
5. Verification queries prove the extension, the table, the vector column's size and that null embeddings are allowed.
6. The similarity search function (`match_properties`) is **not** part of this migration. It comes in a later step, once vectors exist.

## Safe migration order (must not be reordered)

| Order | Step | Why it has to come at this point |
| ---: | --- | --- |
| 1 | Enable the `vector` extension (pgvector) | The `vector` column type and the `<=>` operator don't exist until the extension is on. Creating the column first would fail with "type vector does not exist." |
| 2 | Create the `properties` table with the model's columns and `embedding vector(1536)` (nullable) | It depends on step 1 for the vector type. It's a new table, so nothing existing is altered and `property_listings` is untouched. |
| 3 | Turn on RLS for `properties` and add the read-only select policy | A policy needs the table to exist first. Doing this right after creating the table means the table is never left open in Supabase's public API. |
| 4 | Vector index: **skipped** (see the index recommendation below) | An index could only come after the column exists, and at our sample size it isn't needed. |
| 5 | Run the verification queries | This confirms the shape before any seed data, embedding code or search SQL is written on top of it. |

- **Do not** create the `embedding` column before enabling the extension.
- **Do not** use any size other than 1536, or a second embedding column name.
- **Do not** add seed rows in this migration.

## Similarity approach (beginner demo)

- **Choice:** cosine distance, using pgvector's `<=>` operator. Later search SQL will sort by `embedding <=> query_embedding` **ascending**, so the smallest distance (closest meaning) comes first. If we show a "similarity" score instead, it is `1 - distance`, where higher is better. Whoever writes `match_properties` must say clearly which one it returns (question 3 in `docs/vector-search-learner-notes.md`).
- **Why:** cosine compares the *direction* of two number lists, which is a good stand-in for "do these mean the same thing." It's the common default for text embeddings and works well with OpenAI's embedding models.
- **Tradeoffs:**
  - Cosine vs other options: inner product (`<#>`) is slightly faster but easier to get backwards for a beginner, because pgvector returns it negated. Euclidean (`<->`) also measures size, not just direction. Cosine is the clearest choice for learning.
  - An exact scan vs an index: with no index, Postgres compares the query to every row. That gives perfectly correct results and is instant for about 10 rows, but it would get slow with many thousands of listings.

## Index recommendation

- **Demo scale (8–20 sample rows): no vector index.** A full scan of 20 rows takes a fraction of a millisecond, and it always returns the true nearest matches. An approximate index can skip rows, and it adds settings a beginner would have to tune.
- **Revisit later**, once the table holds thousands of listings. Add an `hnsw` index using the **cosine** operator class (matching the `<=>` choice above) only after most rows have non-null embeddings, and keep the size at 1536.
- An ordinary primary-key index on `id` comes automatically with the table; nothing else is needed.

## Verification queries (run in the Supabase SQL Editor after the migration)

Each check has an intent and a pass condition. The exact SQL can be refined in the migration step.

| # | Intent | Pass when… |
| --- | --- | --- |
| 1 | The `vector` extension is installed | A row named `vector` comes back from the installed-extensions list |
| 2 | `properties` has the model's columns | `id`, `title`, `description`, `city`, `property_type`, `price`, `created_at` and `embedding` all appear, and nothing else |
| 3 | `embedding` is a 1536-length vector | Its type shows as `vector(1536)` |
| 4 | Null embeddings are allowed | Inserting a test row with a title and description but no embedding succeeds (then delete it) |
| 5 | Required text is enforced | Inserting a row with an empty title fails |
| 6 | pgvector operators work | Comparing two small literal vectors with `<=>` returns a number; identical vectors return 0 |
| 7 | RLS is on and read-only | RLS shows as enabled for `properties`, with exactly one select policy and no write policies |

Example sketch (illustrative; the migration step finalizes it):

```sql
-- 1) extension present
select extname, extversion from pg_extension where extname = 'vector';

-- 2 + 3) columns and the vector size
select column_name, is_nullable, format_type(atttypid, atttypmod) as type
from information_schema.columns c
join pg_attribute a
  on a.attrelid = 'public.properties'::regclass and a.attname = c.column_name
where c.table_schema = 'public' and c.table_name = 'properties';

-- 6) operator smoke test (tiny literal vectors, not our table)
select '[1,2,3]'::vector <=> '[1,2,3]'::vector as same,      -- expect 0
       '[1,0,0]'::vector <=> '[0,1,0]'::vector as different; -- expect 1

-- 7) RLS enabled
select relrowsecurity from pg_class where oid = 'public.properties'::regclass;
```

## Out of scope for this migration

- Generating embeddings for listings (the TypeScript embedding helper comes later)
- Seed or backfill data
- The `match_properties` similarity function
- Search API routes and the React search page
- Vector indexes (deferred until the data is large; see above)
- Any change to `property_listings`, `profiles` or Sprint 4's auth and RLS
- Hybrid keyword + vector ranking, filters, re-ranking, multiple embedding models or versions
- Production embedding operations (billing, rate limits, batch jobs)

## Handoff to the next step

The migration must implement **only** order steps 1–3 and the step 5 verification: enable `vector`, create `properties` exactly as listed in the source-of-truth table with `embedding vector(1536)` nullable, turn on RLS with one read-only select policy, then verify.

It must not change the table name, the column names or the 1536 size, add an index, or add seed rows. Any of those changes has to go through `docs/embedding-data-model.md` first.
