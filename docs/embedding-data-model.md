# PREIshare embedding data model

## Purpose

This is a software-ready design for the sample property listings used by semantic search, and for their embedding vectors. It is the contract that later steps must follow: the Supabase pgvector migration, TypeScript types, seed and backfill, and the similarity search function.

It is **not** SQL and not application code yet.

## Sources

- `docs/semantic-search-requirements.md`: example queries, success criteria, in and out of scope
- `docs/embeddings-learner-notes.md`: an embedding is a list of numbers for meaning; generation and storage are separate; misconceptions to watch for
- `docs/vector-search-learner-notes.md`: comparing a query embedding to stored embeddings, top-K, distance vs similarity, review questions for `match_properties`

## Overview

Each **property** is one sample investment listing that PREIshare can show in semantic search (for example a lakeside A-frame, a family home near schools, a downtown condo).

Each property has two kinds of data:

- **Normal fields that people read:** title, description, city, and so on.
- **One embedding column:** a fixed-length list of numbers that captures the meaning of the listing's text.

Search turns the buyer's query into an embedding with the same recipe and model, compares it to these stored vectors, and returns the closest top-K. It does not depend on exact keyword matches.

This is a **separate sample data set for the search demo**, in a new table named `properties`. It does not change the Sprint 4 `property_listings` table or its owner-only RLS (auth and RLS changes are out of scope in the requirements brief).

## Core listing fields (this tutorial slice)

| Field | Type (logical) | Required | Notes |
| --- | --- | --- | --- |
| title | text | yes | Short headline, such as "Lakeside A-frame on a private cove." Not empty. Shown in results. Part of the embedding input. |
| description | text | yes | The longer write-up and the main source of meaning. Not empty. Shown as a snippet in results. Part of the embedding input. |
| city | text | no | Shown next to each result so a tester can judge it. **Not** embedded and not a filter (filters are out of scope). |
| property_type | text | no | Plain label such as cabin, single-family, condo or duplex. Display only; **not** embedded. |
| price | number (whole US dollars) | no | Display only. **Not** embedded, and not used for ranking or filtering. |
| created_at | timestamp | yes | When the row was inserted; set by the database. |

These are the only listing fields for this slice. The requirements brief needs results a stranger can judge (a title, a snippet, a location), and nothing more.

## What text is embedded

**Embedding input (canonical string):** `title`, then a blank line, then `description`.

```
{title}

{description}
```

Example for one sample listing:

```
Lakeside A-frame on a private cove

Peaceful setting with a private dock. Strong short-term rental history every summer.
```

Rules:

- **One recipe everywhere.** Seed, backfill, re-embed and any future insert all build the input with this exact recipe. Code that embeds only the title, or adds the city, is wrong and should be rejected in review.
- **Trim, don't rewrite.** Trim leading and trailing spaces from each field. Don't lowercase, summarize or remove words.
- **No numbers or ids.** Price, ids, city and dates are not embedded, because they aren't narrative meaning and would add noise.
- **Queries are embedded as typed.** The buyer's query text (trimmed) is embedded with the **same model** as the listings. It doesn't use the title/description recipe, because a query is just one string.
- **Raw text stays unchanged.** `title` and `description` are stored exactly as written. The vector is a separate column derived from them, and it doesn't contain the text.

## Embedding column

| Field | Type (logical) | Required | Notes |
| --- | --- | --- | --- |
| embedding | vector(DIMENSION_TODO) | yes, after backfill | One vector per property. Same model and same length for every row and every query. |

### Dimension placeholder

- The vector length is written as **DIMENSION_TODO** in this doc, and **DIMENSION_TODO = 1536** for now. The chosen model is Google `gemini-embedding-001` (free tier), asked for 1536 numbers. (We first planned OpenAI `text-embedding-3-small`, also 1536, and switched to Gemini to stay free; the size did not change.) The real size must match whatever model is finally chosen; if the model changes, this number changes with it.
- **Critical:** query vectors and stored vectors must come from the **same model with the same DIMENSION_TODO length**. A mismatched length breaks inserts or search; a different model with the same length gives meaningless scores.
- When the model is chosen, replace DIMENSION_TODO in one pass in this doc, the migration and the TypeScript types, and write down the model name next to it.

### Nullability and backfill lifecycle

1. **Create:** a sample listing is inserted with its title, description and display fields. `embedding` may be **null** at this point.
2. **Generate:** server code builds the canonical string and sends it to the embedding model, and a DIMENSION_TODO-length list comes back.
3. **Store:** that list is saved into `embedding` on the same row. This is a separate database write.
4. **Searchable:** only rows with a non-null embedding are eligible for semantic search. Rows with a null embedding are skipped, never ranked as fake matches.

- After seed and backfill, **every** sample property must have a non-null embedding. The verification step checks that the count of null embeddings is 0.
- If `title` or `description` changes, the embedding is stale. Regenerate it with the same recipe, or set it back to null until it is.

## Separation of concerns

| Concern | Where it lives |
| --- | --- |
| Human-readable listing | `title`, `description`, `city`, `property_type`, `price` |
| Meaning for search | the `embedding` column only |
| Generating the vector | Server code calling the embedding model (later: a TypeScript helper). The API key stays server-only, per Sprint 4 secret rules. |
| Storing the vector | Supabase Postgres with pgvector |
| Similarity metric | Chosen at query time. Planned: **cosine**. The SQL must make clear whether it returns a distance (lower is better) or a similarity (higher is better). |

Never replace `description` with the vector. You need both: the text for the UI and for re-embedding, and the vector for ranking.

## In scope vs out of scope (data model)

**In scope**

- One sample table named `properties` with `id`, the listing fields above and `embedding`
- One embedding per property
- The canonical embedding input recipe and a single DIMENSION_TODO placeholder
- Null-until-backfilled lifecycle

**Out of scope (do not model yet)**

- Multiple embedding versions or models per property
- User accounts, owners, saved searches, roles or RLS changes
- Photos, documents or other media tables
- Payments, messaging, maps or filter fields (beds, baths, price ranges)
- Full-text keyword indexes as a replacement for vectors
- Production embedding operations: API billing, rate limits, batch-job tables or queues
- Changes to the Sprint 4 `property_listings` table
